# Token Monitor

Agent Sandbox can report Claude Code, Codex, OpenCode and Antigravity CLI usage to a separate Token Monitor Hub. The Docker integration is off by default. It runs on the Docker host and survives ordinary sandbox destruction and recreation. The Google Colab backend has no Token Monitor lifecycle hooks.

## Setup

Use a supported Agent Sandbox Linux Docker host with systemd, rootful Docker, Python 3.10 or later, and a running Token Monitor Hub. Initial provisioning builds a small headless image with upstream Token Monitor, Node.js and its pinned Tokscale dependency. The host needs access to the upstream Docker, Debian, GitHub and npm registries for that build. Running collectors need only the host's configured Hub route.

On the Docker host, from the Agent Sandbox installation directory:

1. Create a private secret file. The command below reads the Hub's shared secret without echoing it or putting it in your shell history.

   ```bash
   (umask 077; set -o noclobber; read -rs -p 'Hub secret: ' secret; printf '%s\n' "$secret" > .token-monitor.secret)
   ```

2. Create `.token-monitor.json` with mode `0600`. Start with this configuration for a Hub bound to the same host:

   ```json
   {
     "enabled": true,
     "hub_url": "http://127.0.0.1:17321",
     "secret_file": ".token-monitor.secret"
   }
   ```

   For a remote Hub, use an HTTPS endpoint such as `https://token-monitor.example.net`. A Hub behind a VPN works when the **host** can resolve and reach it. Keep a local HTTP Hub on loopback or use a trusted encrypted transport. The shared secret rides in the Authorization header. HTTPS certificates are verified against the host's trust store.

3. Run `./scripts/token-monitor.sh setup`. This validates Hub authentication, provisions the release, installs a systemd timer, and attempts a real sync when the workspace is running. When setting up a new Agent Sandbox, `./scripts/setup.sh` performs the same initialization if the configuration is present.

4. Use `./scripts/up.sh` and confirm the device appears in the Hub or connected widget. Run `./scripts/token-monitor.sh status` to see the device ID, recent synchronization state, recovery queue and connectivity. An idle installation without a workspace waits until there is source data to scan.

The Hub can run independently as the upstream Node Hub, in a connected desktop widget, or as a compatible Worker. Keep its own persistent storage and backups according to the upstream deployment guide. [Token Monitor headless agent](https://github.com/Javis603/token-monitor/blob/v0.99.0/docs/headless-agent.md) · [Upstream API reference](https://github.com/Javis603/token-monitor/blob/v0.99.0/docs/API.md)

## Configuration

| Setting | Default | Meaning |
| --- | --- | --- |
| `enabled` | `false` | Enables collection and lifecycle hooks. |
| `hub_url` | Required | Absolute HTTP or HTTPS Hub URL. A reverse proxy base path is allowed. |
| `secret_file` | Required | Path to the file containing the shared secret. Use `.token-monitor.secret` or an absolute path outside the checkout. Set mode `0600`. |
| `interval_seconds` | `300` | Minimum interval between scheduled attempts, from 60 to 86,400 seconds. systemd checks approximately once a minute. |
| `collector_version` | `v0.99.0` | Upstream release tag. The default also verifies the exact upstream commit. Antigravity requires the pinned default because its metadata projection is version-specific. |
| `device_prefix` | `agent-sandbox` | Used when generating the persistent device ID. Changing it afterward leaves the ID intact. |
| `device_id` | Generated | Set the ID before the first setup to adopt an existing collector identity with its upstream session archive. |
| `providers` | `["claude", "codex", "opencode", "antigravity"]` | Usage sources enabled for this installation. |
| `projects_enabled` | `true` | Includes upstream project breakdowns. Set it to `false` to omit project labels, IDs and rollups from Hub uploads. |
| `timezone` | `UTC` | IANA timezone for usage windows and historical calendar dates. Keep the previous collector's timezone when migrating. |

The config and default secret are excluded from Git and Docker build contexts. `destroy.sh` leaves them and `.token-monitor/` in place. Keep the configuration and state on the host. Use a separate shared secret file for each deployment if the Hub topology requires it.

> **Draft security blocker:** Do not enable this implementation yet. A read-only local check found a credential-shaped OAuth token field inside a conversation generation blob, in a protobuf field the pinned scanner does not use. Capture now streams database and WAL bytes to a networkless tmpfs-only projector instead of persisting them, but the scanner-required model and workspace strings can still contain arbitrary sensitive values. The projector rejects some credential-shaped strings, which can also reject a legitimate model or project path; this does not prove that every credential format is excluded. The observed value was not printed or committed. Older Draft snapshots may contain unprojected raw data and are refused by the collector; preserve them securely for recovery.

## Enable Antigravity on an existing installation

Update the host checkout to a release containing this support. Leave the workspace and its agents running. Before changing providers, run `./scripts/token-monitor.sh sync` and check `./scripts/token-monitor.sh status` until the recovery queue is empty; retain a private backup of `.token-monitor/` and the configuration. If `.token-monitor.json` has an explicit `providers` list, add `"antigravity"` to that list, keeping every other setting and provider unchanged. An omitted list uses the new default automatically. Existing explicit exclusions remain in force; only add the providers you intend to collect. Keep the file mode `0600`.

Run `./scripts/token-monitor.sh setup` to build the updated collector image and synchronize, then check `./scripts/token-monitor.sh status` and compare the Hub device ID, existing totals and project breakdowns. This updates the collector and managed systemd integration without restarting or rebuilding the sandbox. It keeps the device ID, archive and Hub secret in place. Historical Antigravity conversations still present in the workspace are imported on the first successful scan; previously deleted and never captured conversations cannot be recovered.

## Operation and recovery

- `./scripts/token-monitor.sh sync` starts an immediate attempt, including any queued recovery snapshot. The periodic schedule is managed by systemd. A shared lock serializes scheduled, manual and final jobs. Hub failures back off exponentially up to one hour. A separate attempt can be started manually once connectivity returns.
- `./scripts/stop.sh` captures final usage and stops the workspace. Add `--down` to remove the containers while preserving normal sandbox credentials. `./scripts/up.sh --rebuild` and `./scripts/destroy.sh` also capture final usage before container removal. Update older systemd services to call `scripts/stop.sh` on shutdown.
- During controlled shutdown the host holds a descriptor to the workspace filesystem across Docker's graceful stop. It snapshots records after writers exit, then attempts ingestion. If the Hub fails, the snapshot stays in a private queue and is retried even after container removal. If the host cannot commit the final snapshot, the removal stops with a diagnostic. A workspace already stopped by raw Compose must be resumed with `scripts/up.sh` before the final capture can be verified.
- The final hook is bounded by a four-minute timeout and a 15-second forced termination allowance. `./scripts/destroy.sh --yes --force` opts out of final accounting and proceeds with destruction. `./scripts/stop.sh --down --force` does the same for a reset that preserves credentials. The queue retains up to four generations, each limited to 8 GiB, with a 2 GiB per-file limit. The upstream container uses one CPU, 2 GiB of memory and a 120-second job timeout. An Antigravity source database, sidecars and projected output must fit together in the sanitizer's 1 GiB private work area. OpenCode databases with sidecars must fit in the collector's 1 GiB private work area.
- If `status` reports queued work, leave `.token-monitor/` intact and correct the reported failure. Use `sudo journalctl -u agent-sandbox-token-monitor.service -n 30` for scheduled errors. For an HTTP 401 or 403, verify the Hub secret. If no ingest was sent, check the collector version and storage limits. Failures starting Docker or reading a source may require checking the Docker service and workspace state. The Docker logs for collector containers are disabled.
- Run `./scripts/token-monitor.sh uninstall` to remove the managed timer and disable lifecycle hooks. It moves the configuration into `.token-monitor/disabled-config-*.json` and keeps the local archive, snapshots, secret, collector image and Hub history for rollback. Restore the saved config to `.token-monitor.json` with mode `0600` and rerun setup to re-enable it. Remove cached collector images separately with Docker if desired.

### Device identity, deletion and restore

The upstream Hub replaces a device's snapshot when it receives the same device ID. It combines different device IDs without cross-device deduplication. This integration uses one installation ID across restarts and empty recreations, with a persistent upstream usage archive. When a session disappears, the collector can replay its last retained observation. Restoring the same session source to the same installation does not add a second session. If a restored observation is older or reports a lower token count, the collector keeps the archived version and continues importing other sessions. Agent Sandbox selects which version to pass to Token Monitor. The upstream collector still computes, projects and archives the usage figures.

Keep a host backup of `.token-monitor/` together with its configuration and the Hub's own data. The entire Antigravity compact archive directory (including its hidden index and checksum files) and its `antigravity-usage-required` marker under `.token-monitor/collector/` must travel with the upstream session archive and device ID; restoring only one can lead to incorrect deduplication. Restore the usage sources to the same installation or migrate the device ID and archive together. Restore or transfer a single lineage and keep its original collector off. Concurrently publishing a copied workspace under another ID double counts its sessions. A later observation can advance its session total. A resumed fork that reuses the same provider session ID cannot be added to the original as independent usage, because Token Monitor identifies both as the same session. Start a distinct provider session when continuing from an old transcript if you need both branches accounted for separately. For older dates outside the collector’s session-level daily window, the collector keeps existing day history for providers with stale observations. Separate sessions from those days still import into all-time totals. A fresh daily breakdown for a mixture of old and new records on such a day may be incomplete.

An unsolicited container removal, a host crash before the snapshot, or provider records deleted before any successful scan can lose unobserved usage. The Hub keeps ingested history when the workspace is removed. Hub storage durability is owned by the Hub deployment. A standalone Hub batches disk writes and flushes on graceful shutdown. Preserve its data volume across restarts.

### Project attribution

The upstream collector reads project metadata from the original provider records. Claude Code can fall back to the transcript's recorded working directory when its encoded project directory cannot be resolved. Codex uses the rollout's workspace metadata, including from compressed archives. OpenCode uses the stored session directory or legacy message workspace. Antigravity CLI uses the workspace URI in its conversation database. Agent Sandbox keeps the first known project identity for an archived session across resets, restored paths and migration. Usage with no usable workspace remains in overall and provider totals.

The Hub groups projects by the upstream canonical folder label, which ignores case and normalizes Unicode. Checkouts called `Payments` and `payments` aggregate even when their device IDs and absolute paths differ. Unrelated checkouts with the same folder name also aggregate. Checkouts with different folder names stay separate even if they share a remote. Native project IDs hash the recorded paths. They are device observations, so IDs can differ across checkouts that the Hub groups under one label.

The collector receives only staged provider records. Repositories, Git config, remotes and worktree pointer files from the workspace are outside the stage. It can reuse project attribution already captured in an archive and worktree relationships that the scanner can derive from recorded paths. An unseen worktree that needs Git metadata to identify its parent stays under its recorded folder label. A Claude Code slug with no recoverable path remains unattributed. Upstream upload limits can mark a project breakdown incomplete on very large devices. The core token and cost totals remain available.

## Migration from a host collector

1. Identify the old collector's Hub URL, device ID, timezone, clients and private usage archive directory. Keep the old setup, credential store and service definitions for rollback. Do this on the Docker host without copying provider credentials.
2. Stop the external timer and any in-flight collector before switching. Avoid running both collectors during migration. Take a filesystem backup of the old archive directory after its writer exits and back up the Hub storage.
3. Set `device_id` to the old ID and source the Hub secret from a protected file. Use the same timezone and providers, and leave project accounting enabled to retain the existing Hub breakdowns. Before setup, prepare root-owned `.token-monitor/` with mode `0700` and a `.token-monitor/collector/archive/` subdirectory. Copy just the upstream `session-usage-archive.sqlite` (with any required SQLite sidecars from the stopped writer), legacy `session-usage-archive.json`, `daily-history-archive.json`, and `daily-history-calendars.json` files that exist. Set the archive directory and copied files to UID/GID `65532:65532`. Keep the rest of the old state in the backup. In particular, omit authorization journals, PID files, provider auth and scanner caches. The integration requires a session archive when first adopting an explicit ID or when the local status records a previous successful upload. This protects the Hub if the archive was omitted during migration or lost from a partial host backup.
4. Before cutover, keep a copy of the existing Hub's project breakdowns and verify the exported session archive contains the corresponding project labels. A Hub rollup by itself cannot identify the sessions or recover project attribution absent from both the archive and provider records. Test such a legacy migration against a Hub copy before switching the live device. Run setup and compare existing all-time counts, costs, project totals and device ID with the previous Hub view. Compare after the first real upload, including previously deleted sessions. If migrating from a collector that synced titles, follow the upstream title revocation instructions with the original collector and credentials.
5. To roll back, run the native uninstall command first. Then resume the previous timer with its untouched configuration and archive. If either archive has imported new usage since the cutover, save both states and the Hub backup before publishing again under the shared ID.

## Maintenance and performance

To upgrade, back up `.token-monitor/`, drain any pending recovery queue, set the desired `collector_version`, and rerun setup. Setup reuses the image when the version and build inputs match. Test new releases against an isolated Hub before switching production. The integration relies on upstream archive, period projection and daily history APIs, scanner paths, and the authenticated full-ingest protocol.

Claude and Codex records are copied only from the supported project, session and archived-session directories, including Codex's Zstandard archives. A capture preserves file bytes and modification times, and rejects a generation if a record changes during its read. The upstream scanner decides how to interpret a stable JSONL tail, including a final valid record without a newline. OpenCode collects legacy messages and SQLite databases. Antigravity CLI reads only `.gemini/antigravity-cli/conversations/*.db` and their SQLite WAL or rollback journal sidecars; summary databases, standalone protobuf files, credential files, logs and other Gemini configuration are excluded. Each stable source pair is streamed into a separate networkless, non-root worker, recovered on private tmpfs, and projected to the fields required by the pinned scanner before the host writes a snapshot. Response IDs are replaced by stable SHA-256 digests for deduplication. The conversation database itself can contain credential-shaped text; accepted model, workspace and session filename strings are not proven secret-free. Recognizable credential patterns in these strings cause capture to fail, including possible false positives. DB and WAL identities are checked before and after streaming. SQLite is processed only in isolated workers on private copies. A WAL checkpoint during capture causes a retry. A changing database and its WAL are streamed together and recovered in a worker's private work area; unchanged projected files are reused. The projection is tied to the pinned v0.99.0 collector, so other collector versions cannot be selected while Antigravity is enabled. Each capture starts one sanitizer container and runs a separate worker process per changed conversation. Many or large conversations increase traversal, worker startup, staging and scanner time and can exhaust the snapshot or work-area limits. Unchanged projected conversations are reused. Docker must report swap-limit support; the sanitizer uses a memory limit with swap disabled so its temporary raw data is not swapped by that cgroup. The worker expires after four minutes even if its controller is interrupted. Provider-specific custom paths are outside the supported scope. The collector image downloads Tokscale's public pricing catalogs at build time. The networkless collector uses those catalogs and upstream pricing logic to estimate costs. A model missing from the bundled catalogs can have unknown pricing until the image is rebuilt with newer catalogs.

### Antigravity coverage and limitations

The pinned Tokscale scanner reads each conversation's `gen_metadata` and workspace metadata directly; it uses reported response model IDs and token components, with upstream model aliases and pricing. It deduplicates repeated response IDs across the Antigravity family, including independent conversations; records without a stable response ID cannot be matched this way. The collector keeps compact copies of the scanner-required generation, timestamp and workspace columns under `.token-monitor/collector/antigravity-usage/`. It scans those copies alongside current conversations so that response IDs remain available for deduplication after a source is deleted. Older observations whose generation rows are a subset of the retained copy do not replace it. A rewritten row can advance when it has the same hashed response ID, unchanged model and timing fields, and nondecreasing reported token counters. Changes involving a fallback output representation remain conservative because larger raw counters alone can reduce reported output. The upstream scanner still calculates usage and cost. The retained workspace and step metadata cannot be dropped by an update. Disjoint generation rows from a restored conversation can also be retained together only when every row has a stable response ID, shared indices match exactly, the old metadata is preserved and a valid session timestamp anchors fallback dating. Other conflicting versions stop collection rather than silently discarding or duplicating usage; restore a compatible source or the original backup before retrying. The compact archive has an 8 GiB limit and is needed together with the upstream archive to retain deduplication across restore or migration. Its inventory and per-file checksums detect missing or modified retained databases before scanning. A write-ahead checksum permits recovery on either side of an interrupted database replacement. Restore the entire directory from one consistent backup; upgrading a legacy inventory can only checksum the bytes that are present at upgrade time. A synthetic parent/child fixture with the same response ID counts that response once and reports separate planner and worker models. With the ID omitted from both copies, the pinned scanner counts both; this is a demonstrated limitation, not evidence that a real parent necessarily duplicates a child. The fixture's parent-reference data is illustrative only, and the scanner does not consume it. The pinned parser does not establish parent-child relationships between CLI conversation databases or prove that parent aggregates exclude child usage. Orchestrator and subagent accounting therefore remains unverified and may double count if Antigravity records the same usage in both; individual worker attribution depends on the model identity present in each generation. Generic routing labels or unknown models may lack reliable attribution or pricing. Tokscale contains price aliases for some known orchestrator and worker routes. An isolated synthetic fixture confirms that explicit `gemini-pro-orchestrator-neon` and `gemini-flash-worker-agy` response model IDs appear separately with their respective catalog-based estimates. A read-only comparison of 43 stable real conversation databases found identical upstream reports from the originals and compact copies; three sessions contained both orchestrator and worker route labels. The comparison retained no raw fixtures. Those databases had no populated parent-reference rows or subtrajectory flags, so the comparison does not establish that real child records always report a model, that every worker model is identified, or that child usage is disjoint from parent usage. No inferred worker usage is added by this integration.

An isolated streaming capture of 10 small synthetic conversation databases took 2.836 seconds cold and 0.003 seconds unchanged; it copied 81,920 source bytes cold and reused all projected files on the unchanged pass. These timings exclude collector startup and Hub upload. A cold import starts one worker process per database, so large histories can still approach the lifecycle timeout.

An isolated compact-archive sample with 1,000 synthetic generation rows in one 10,248,192-byte database took 0.237 seconds on first retention and 0.134 seconds unchanged with checksum verification. It excludes source capture, SQLite recovery, scanner execution and Hub upload. A changed database requires a full compact copy and comparison, so large histories can take substantially longer and consume additional host storage.

A local benchmark used 1,000 Codex-shaped JSONL files covering 303,600,000 bytes on a Linux host. It measured snapshot construction, including metadata traversal and fsync:

| Snapshot | Copied | Elapsed |
| --- | ---: | ---: |
| Cold | 303,600,000 bytes | 0.385 s |
| Unchanged | 0 bytes | 0.078 s |
| One appended record | 304,612 bytes | 0.083 s |

All passes inspect file metadata to detect replacement and deletion. The unchanged pass hard-links previously copied files inside private host state. Changed files are recopied in full, and a changed SQLite database may require copying its WAL pair and materializing it in the collector. The official agent does its own scan on each synchronization. The timings exclude that scan, Hub upload and Docker startup.

A separate comparison used the same 304 sessions and 44 project labels in two isolated collectors. Elapsed time covers container startup, collection and the Hub acknowledgement. Wire size is the JSON request body. Archive size includes the persisted upstream archive files after the third sync.

| Project accounting | Cold | Warm (mean of two) | Ingest bytes | Archive bytes |
| --- | ---: | ---: | ---: | ---: |
| Disabled | 5.955 s | 4.021 s | 227,087 | 1,296,056 |
| Enabled | 4.547 s | 3.752 s | 271,201 | 1,296,056 |

Project accounting added 44,114 bytes per upload in this fixture. Each collector staged the same 143,574 source bytes. The short timing sample did not resolve a runtime penalty.

The isolated lifecycle tests capture a final Antigravity SQLite write, preserve a projected snapshot through a Hub outage and workspace removal, and retain totals after an empty workspace recreation. They do not exercise the production sandbox or prove owner sign-off. An isolated setup-upgrade test starts with an explicit three-provider list and a running fixture workspace, then adds Antigravity and reruns setup. It checks the workspace PID and start time, device ID, secret, existing archived totals and projects, and managed unit file contents and inodes. Systemd calls are mocked and the fixture process is not a real coding agent.

The integration tests start a disposable Hub and Docker containers. To run them, install the upstream checkout's production npm dependencies, build the collector image for the same version, and set `TOKEN_MONITOR_TEST_UPSTREAM` and `TOKEN_MONITOR_TEST_IMAGE` to their respective checkout path and image tag. Run `python3 -m unittest discover -s tests -p 'test_token_monitor*.py' -v` from Agent Sandbox.

## Trust boundary

The sandbox bridge, firewall and Docker mounts remain the same. No integration port is opened to the workspace. A root-owned host job reads the verified local workspace's Linux mount namespace through a file descriptor. It selects only usage paths and rejects symlinks, hard links, different mounts and special files. Transcripts are staged in a private host directory, and only the selected stage is mounted read-only.

The official collector runs as a dedicated non-root UID in a read-only Docker container with no external network, capabilities, host Docker socket, or provider credentials. It receives only the stage, its own archive, and a private Unix socket. The host relay permits a bounded Token Monitor ingest request for the configured device, checks its acknowledgement, and attaches the Hub secret on the host side. It strips error response bodies and refuses redirects. Limits, ambient OpenCode quota collection and title synchronization are disabled. Project accounting sends workspace-folder labels and opaque path-derived IDs to authenticated Hub readers. Absolute workspace paths stay local. Set `projects_enabled` to `false` to omit this metadata from uploads. Previously sent data is subject to the Hub's retention and backup policy. Token Monitor controls the remaining summary contents, estimated costs, archive reconciliation and Hub retention.

Usage files are controlled by the providers and by any agent that can write them. A sandbox can falsify its own reported usage and exhaust its snapshot budget. Clock errors can skew period selection. Raw staged transcripts are sensitive and may contain prompts or tool output. Acknowledged raw data is kept only as a cache while the workspace is active. The Antigravity compact archive persists selected opaque metadata blobs, including workspace paths, until its host state is removed; these may contain sensitive data and must be backed up and protected with the rest of `.token-monitor/`. A pending stage stays private until delivery. Keep the host state and Hub restricted to the administrators and readers who should see that data.
